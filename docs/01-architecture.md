# Backend Architecture

Status: design, approved for scaffolding · Last updated: 2026-10-19

This document fixes the decisions the rest of the backend is built on. The data
model itself lives in [`db/schema.sql`](../db/schema.sql); the HTTP contract in
[`02-api-design.md`](02-api-design.md).

---

## 1. Decisions at a glance

| Area | Decision | Why |
|---|---|---|
| Language / framework | **Python 3.13+, Django (current LTS) + Django REST Framework** | Python's `Decimal` is exact and built in (JavaScript has no decimal type, a constant source of money bugs). Django gives migrations, auth primitives, an admin panel for support staff, and a huge, stable ecosystem. One person can move fast in it for years. |
| Database | **PostgreSQL 17+** | ACID transactions, Row-Level Security, CHECK constraints, partial indexes, generated columns, JSONB. Financial data needs all of these. |
| Architecture | **Modular monolith** | One deployable, clear internal modules. Microservices would add network failure modes and distributed transactions with no benefit at this scale. |
| Multi-tenancy | **Shared schema + `tenant_id` + Postgres RLS + composite FKs** | Scales to thousands of tenants with one migration path; isolation is enforced by the database, not just by remembering a filter in every query. |
| Background jobs | **Celery + Redis** | PDF generation, email/WhatsApp sending, report exports, later e-invoice (IRP) API calls. |
| File storage | **S3-compatible object storage** (AWS S3 Mumbai / Cloudflare R2), presigned URLs | Files never pass through or live on the app server. |
| API contract | **REST, `/api/v1`, OpenAPI 3.1 generated by drf-spectacular** | Web and mobile share one API; typed clients can be generated from the spec. |
| Hosting | **India region** (e.g. AWS ap-south-1) | Data residency expectations of Indian businesses; DPDP Act. |
| Local dev | **Docker Compose** (Postgres, Redis, SeaweedFS for S3, Mailpit) | Same services locally as in production. SeaweedFS replaces MinIO, which stopped publishing container images in 2025. |

Alternatives considered: NestJS (good, but no native decimal and you'd rebuild
the admin); Go (excellent runtime, slower to build CRUD-heavy business apps);
Spring Boot / .NET (solid, heavier for a small team). None is wrong; Django is
the best fit for a small team building a money-heavy business app.

## 2. Multi-tenancy

### 2.1 Model

* A **tenant** is one business (a construction company or contractor).
* A **user** is a global identity. **Memberships** link users to tenants with a
  role, so an accountant can serve several firms with one login.
* Every business table carries `tenant_id`. The only global tables are
  `users`, `tenants` (itself protected by RLS) and `auth_sessions`.

### 2.2 Three layers of isolation

1. **Application layer.** The tenant comes from the signed access token, never
   from a client-controlled header or URL. Querysets go through a tenant-aware
   manager.
2. **Row-Level Security.** Every tenant table has a policy
   `tenant_id = app_current_tenant()`, with `FORCE ROW LEVEL SECURITY`. A
   forgotten `.filter(tenant=...)` returns nothing instead of another
   company's invoices. With no tenant set, queries return **zero rows** (fail
   closed).
3. **Composite foreign keys.** Postgres skips RLS during FK checks, so
   `documents.party_id → parties.id` alone would let tenant A attach tenant B's
   party if it learned the uuid. Every reference is
   `(tenant_id, party_id) → parties (tenant_id, id)`, so cross-tenant links
   cannot exist.

### 2.3 Request lifecycle

```
HTTP request
  └─ RequestIdMiddleware        server-generated UUIDv7 request id
  └─ AuthenticationMiddleware   verify JWT → request.principal (user_id, tenant_id, role)
  └─ TenantContextMiddleware    BEGIN
                                SELECT set_config('app.tenant_id', :tenant, true),
                                       set_config('app.user_id',   :user,   true),
                                       set_config('app.request_id', :req,   true);
     └─ View (ATOMIC_REQUESTS)  SAVEPOINT; ordinary ORM queries; RLS filters every row;
                                an error rolls back to the savepoint
  └─ COMMIT / ROLLBACK          settings vanish with the transaction
```

Django's `ATOMIC_REQUESTS` wraps only the view, so the middleware opens the
request transaction itself (`apps/core/middleware.py`) and the view's atomic
block nests inside it as a savepoint. Requests without a principal get no
transaction and no tenant: RLS returns nothing.

Celery tasks, management commands and tests do the same through
`apps.core.tenancy.tenant_context(tenant_id, user_id)`: every task receives
`tenant_id` and `user_id` explicitly. Switching to a different tenant while a
context is active raises; when nested in a longer transaction the settings
are cleared on exit.

### 2.4 Rules that must never be broken

These are the classic ways RLS-based tenancy leaks. Each one gets a test.

| Rule | What goes wrong otherwise |
|---|---|
| Always `set_config(..., true)` (transaction-local), never plain `SET` | With connection pooling (PgBouncer/pgpool), the next request on that connection inherits the previous tenant. |
| The app connects as `billing_app`: not the table owner, `NOBYPASSRLS`, never superuser | Owners and superusers bypass RLS. |
| Every view is `WITH (security_invoker = true)` | A normal view runs as its owner and silently returns all tenants' rows. |
| Every FK between tenant tables is composite with `tenant_id` | FK checks bypass RLS, allowing cross-tenant references. |
| No globally unique business keys (only `users.email`) | Unique-constraint violations reveal another tenant's data ("GSTIN already exists"). Uniqueness is per tenant. |
| Migrations run as `billing_owner`; data migrations set tenant context per tenant or use a dedicated, audited BYPASSRLS role | A data migration that sees zero rows looks like it succeeded but did nothing. |
| Platform support access uses a separate audited role, never the app role with RLS disabled | "Temporarily" disabling RLS in production becomes permanent. |

### 2.5 Django specifics

* Django owns tables and simple constraints; RLS policies, triggers, composite
  FKs, grants and views are applied by `RunSQL` migrations copied from
  `db/schema.sql`.
* Django has no composite foreign keys. Models declare a normal `ForeignKey`
  (useful for joins) **and** the migration adds the composite FK constraint.
* `DATABASES['default']['ATOMIC_REQUESTS'] = True`, plus a `tenant_context()`
  context manager for tasks, management commands and tests.
* The app generates **UUIDv7** primary keys (`uuid.uuid7()`, Python 3.14+, or
  the `uuid6` package before that). They sort by creation time, which keeps
  B-tree indexes compact.

## 3. Roles & permissions

Roles are per membership (per tenant). Permission checks live in one module
(`core/permissions.py`) and are named by action, e.g. `documents.issue`.

| Capability | OWNER | ADMIN | ACCOUNTANT | SITE_ENGINEER | VIEWER |
|---|:-:|:-:|:-:|:-:|:-:|
| Business settings, GST registrations, number series | ✓ | ✓ | | | |
| Invite / change members (ADMIN cannot touch OWNER) | ✓ | ✓ | | | |
| Create / edit parties, projects, catalog | ✓ | ✓ | ✓ | | |
| Edit BOQ and measurements | ✓ | ✓ | ✓ | ✓ | |
| Create / edit **draft** documents | ✓ | ✓ | ✓ | ✓ | |
| **Issue / cancel** documents, credit & debit notes | ✓ | ✓ | ✓ | | |
| Record / void payments | ✓ | ✓ | ✓ | | |
| Record expenses | ✓ | ✓ | ✓ | ✓ | |
| Dashboards & reports | ✓ | ✓ | ✓ | | ✓ |
| Audit log | ✓ | ✓ | | | |
| Transfer ownership / close tenant | ✓ | | | | |

Implemented in `apps/core/permissions.py` (`ACTIONS`, `can`, `require`,
`HasAction`); `tests/core/test_permissions.py` checks this table cell by cell.
Member rules on top of the matrix: nobody changes or revokes their own
membership; an ADMIN cannot touch an OWNER or appoint one; a tenant always
keeps an active OWNER. Revoking a member or changing their role signs out
their sessions for that tenant immediately (stricter than "within 10 minutes").
New members are **invited** (status INVITED) and join only when they accept.
An invitee can read the inviting tenant's row (to see who invited them) and
nothing else of it; accepting goes through the database function
`respond_to_invitation()`, the only path that may update a membership of a
tenant the user is not signed in to, and it changes nothing but the status.

Later: project-level scoping (site engineers see only assigned projects) via a
`project_members` table plus an extra RLS predicate.

## 4. Module layout

```
backend/
  config/                 settings (base / dev / test / prod), urls, celery, asgi/wsgi
  apps/
    core/                 tenant context middleware, base models, permissions,
                          idempotency, error handling, pagination
    accounts/             users, auth (login, MFA, refresh rotation), memberships
    tenants/              tenant signup, settings, GST registrations, number series
    parties/              customers, vendors, subcontractors
    projects/             projects, BOQ items
    catalog/              reusable items / rates
    documents/
      models.py
      services/           create_draft, update_draft, issue, cancel, convert, credit_note
      tax/                pure tax engine (no Django imports), table-driven tests
      pdf/                templates + renderer (Celery task)
    payments/             payments, allocations
    expenses/
    reports/              dashboard + reporting endpoints over the SQL views
    files/                attachments, presigned upload/download
    audit/                read-only audit log API
  tests/
    tenancy/              cross-tenant attack tests, run against every endpoint
docker-compose.yml
```

Rule: **views stay thin, services hold the business rules, models hold data.**
Services are plain functions taking explicit arguments, which makes them easy
to test and to reuse from Celery and management commands.

## 5. Billing documents

### 5.1 One table, many types

All billing documents share `documents` / `document_lines`. The `doc_type`
decides behaviour:

| doc_type | Purpose | GST book | Revenue |
|---|---|:-:|:-:|
| QUOTATION | Estimate / offer to client | | |
| PROFORMA | Advance request, RA bill preview | | |
| TAX_INVOICE | GST invoice (incl. RA bills of a registered contractor) | ✓ | ✓ |
| BILL_OF_SUPPLY | Composition / unregistered supplier, exempt supply | | ✓ |
| CREDIT_NOTE | Reduces an invoice (rate change, deduction, error) | ✓ | − |
| DEBIT_NOTE | Increases an invoice | ✓ | ✓ |

The owner's **"GST", "non-GST" and "combined"** views are filters on
`is_gst_document` / `is_revenue`, all from the same data with nothing to
reconcile. This also keeps the product clear of "parallel books": a
GST-registered tenant cannot issue a non-GST bill for a taxable supply,
because the database only lets a `REGULAR` registration issue `TAX_INVOICE`
and only non-regular registrations issue `BILL_OF_SUPPLY` (enforced at issue
time).

### 5.2 Lifecycle

```
            ┌──────── delete (drafts only)
            │
 create → DRAFT ──issue──► ISSUED ──cancel──► CANCELLED
                              │
                              ├── (quotation) accept/decline ──► ACCEPTED / DECLINED
                              ├── convert ──► new DRAFT (quotation → invoice)
                              └── credit/debit note ──► new DRAFT referencing it
```

Invariants enforced **in the database** (and tested; see §8):

* Created only as DRAFT; a number is assigned only at issue.
* At issue: at least one line, header totals equal the sum of lines, document
  type allowed for the registration, CGST+SGST vs IGST consistent with the
  place of supply.
* After issue the content is frozen (trigger). Only status, settlement and
  PDF link can change. Lines are frozen too.
* Issued documents cannot be deleted; cancelling requires a reason and zero
  settlements.
* Numbers are unique per GSTIN per financial year, at most 16 characters.
* `amount_settled` changes only through allocations, can never exceed
  `net_receivable` (so over-payment is impossible), and the app role has no
  UPDATE right on it.

### 5.3 Issuing: gapless numbering under concurrency

```python
@transaction.atomic
def issue(document_id, user):
    doc = Document.objects.select_for_update().get(pk=document_id)   # lock the draft
    assert_can_issue(doc, user)
    series = (DocumentSeries.objects.select_for_update()            # lock the counter
              .get(registration=doc.gst_registration, doc_type=doc.doc_type,
                   fy_start_year=fy_of(doc.doc_date), is_active=True))
    number = f"{series.prefix}{series.next_number:0{series.pad_width}d}"
    series.next_number += 1
    series.save(update_fields=["next_number", "updated_at"])
    doc.doc_number, doc.series = number, series
    doc.supplier_snapshot = snapshot(doc.gst_registration)
    doc.party_snapshot = snapshot(doc.party)
    doc.status, doc.issued_at, doc.issued_by = "ISSUED", now(), user
    doc.save()                        # DB trigger re-verifies totals and rules
    enqueue_on_commit(render_pdf, doc.id)
```

The row lock on the series serialises issuers. If anything fails, the whole
transaction rolls back, including the counter, so **no gaps**. Never use
`MAX(number) + 1`.

### 5.4 Tax engine

A pure Python package (`documents/tax/`) with no Django imports.

* All arithmetic in `Decimal`; quantize with **`ROUND_HALF_UP`** (Python
  defaults to banker's rounding, which does not match GST practice).
* Per line: `taxable = round(qty × rate, 2) − discount`; tax per line, rounded
  to paise; CGST = SGST = half the rate on intra-state supplies, IGST on
  inter-state ones.
* **Place of supply for construction = the site's state** (immovable
  property), taken from `projects.site_state_code`, not the client's address.
* Optional invoice round-off to the nearest rupee (stored in `round_off`,
  ±₹1).
* Deductions after tax: retention, income-tax TDS (s.194C), GST TDS (s.51,
  2% for government clients), mobilisation advance recovery →
  `net_receivable`.
* GST rates are data (on catalog/BOQ items), never constants in code, because
  rates change (they did in 2025).
* Hundreds of table-driven test cases, including real invoices checked by a CA.

### 5.5 RA (running account) bills

An RA bill is a `TAX_INVOICE` (or `BILL_OF_SUPPLY`) with `is_ra_bill = true`,
a per-project `ra_sequence`, and lines linked to `boq_items`. Each line stores
the quantity **in this bill** plus a snapshot of the cumulative quantity
billed before it, so the PDF can print "previous / this bill / up to date"
columns without recomputing history. Billing beyond the BOQ quantity is
allowed only for items flagged as variations.

## 6. Security baseline

**Identity & sessions**
* Passwords hashed with Argon2id (`django[argon2]`), checked against a breached
  password list, minimum 10 characters.
* **TOTP MFA required for OWNER and ADMIN**, optional for others; recovery codes
  hashed. Enforced by the default permission `MfaSatisfied`: until the token's
  `amr` contains `otp`, an OWNER/ADMIN can only reach the enrolment endpoints.
  TOTP secrets are AES-256-GCM encrypted (user id as associated data); the
  last accepted time step is stored, so a code cannot be replayed.
* Access token: JWT, 10 minutes, contains `sub`, `tid` (tenant), `role`, `sid`.
  Refresh token: opaque, random, 30 days, stored as SHA-256, **rotated on every
  use, with reuse detection** (reusing a rotated token revokes the whole
  family).
* Web: refresh token in an `HttpOnly; Secure; SameSite=Strict` cookie, access
  token in memory. Mobile: refresh token in Keychain/Keystore.
* Membership/role re-checked at every refresh, so revoking a member takes
  effect within 10 minutes. Revoking all sessions is available instantly.

**Abuse prevention**
* Rate limits (Redis): login 5/min per account and 20/min per IP, with
  progressive lockout; password reset 3/hour; general API 600/min per user.
  (Built so far: per-account progressive lockout in the database, 5 failures →
  1, 2, 4 … minutes, capped at 1 hour. The Redis limits are still to do.)
* Generic auth errors ("invalid email or password") and identical timing, so
  attackers can't enumerate accounts.
* Idempotency keys on all money-moving POSTs.

**Input & output**
* Every request body validated by a serializer with explicit fields (no
  `fields = "__all__"`), max lengths and decimal precision.
* ORM / parameterised SQL only; raw SQL reviewed.
* Strict CORS allow-list, security headers (HSTS, CSP for any server-rendered
  page, `X-Content-Type-Options`, `Referrer-Policy`), TLS 1.2+ only.
* Errors never leak stack traces or SQL; they include a `request_id` for
  support.
* PDF templates auto-escape; no user-controlled template content (prevents
  template injection).

**Files**
* Upload via presigned PUT URL with fixed content type and size; the server
  later verifies size, type (magic bytes) and SHA-256, then marks the file
  AVAILABLE. Buckets are private; downloads use short-lived presigned GET URLs
  after a permission check. Malware scan before AVAILABLE (ClamAV task).

**Data protection & privacy (DPDP Act 2023)**
* Encryption in transit and at rest (RDS / S3 encryption). Application-level
  envelope encryption for secrets such as TOTP keys and future API credentials
  (e-invoice portal).
* Collect only what's needed; PII never in logs (structured-log redaction
  filter).
* Tenant data export (JSON/CSV) and tenant closure with a defined retention
  period. GST law requires keeping records for about 6 years after the annual
  return, so "delete" means close and purge after the legal retention.
* Breach response runbook: detection, containment, notification.

**Supply chain & secrets**
* Secrets in the environment / a secrets manager, never in git. Separate keys
  per environment.
* Pinned dependencies (`uv` lockfile), Dependabot, `pip-audit` and `bandit` in
  CI, container image scanning.

**Audit**
* Every insert, update and delete on business tables is recorded by a database
  trigger with the actor, request id, and before/after values. The app cannot
  modify or delete audit rows, and the table blocks UPDATE/DELETE/TRUNCATE even
  for the owner. This meets the audit-trail requirement for accounting
  software under the Companies (Accounts) Rules.
* Security events (logins, MFA changes, failed logins, role changes, session
  revocations) go to a separate security log.

## 7. Operations

* **Environments:** local (Compose) → staging → production, each with its own
  database and secrets.
* **CI:** lint (ruff), type-check (mypy), tests against real Postgres, security
  scans, migration check (`makemigrations --check`).
* **Backups:** managed Postgres with point-in-time recovery (≥ 7 days) plus
  nightly logical dumps to a separate account/region, encrypted. **Restore
  drill every quarter.**
* **Observability:** JSON logs with `request_id` / `tenant_id`; Sentry for
  errors; `/healthz` (liveness) and `/readyz` (DB + Redis); slow-query log.
* **Migrations:** backwards-compatible (expand → migrate → contract) so deploys
  need no downtime.

## 8. Testing strategy

| Layer | What |
|---|---|
| Tax engine | Table-driven unit tests; property tests (Hypothesis) checking totals = sum of lines and CGST = SGST. |
| Database invariants | Tests that try to break each trigger/constraint (see the verification list below). |
| Tenancy | For **every** endpoint: tenant B's token tries to read, list, update, delete and reference tenant A's objects and must get 404. Generated automatically from the URL conf so new endpoints can't skip it. |
| Concurrency | Two threads issue documents from the same series at once: numbers stay unique and gapless. Two allocations racing on one invoice: no over-payment. |
| API | Contract tests against the OpenAPI schema. |

Schema verification already done (PGlite / PostgreSQL 17, 32 checks, all
passing): tenant isolation on read, write and update; fail-closed without
context; composite-FK cross-tenant block; tenant switcher visibility; issue
rules (no lines, totals mismatch, wrong supply type, duplicate number,
draft-only creation); immutability of issued documents and lines; bill of
supply cannot carry tax; allocation limits and DB-owned `amount_settled`;
cancel requires zero settlements; views respect RLS; audit rows written,
tenant-scoped, unforgeable and append-only; payments cannot be hard-deleted.
These move into the pytest suite when the Django project is scaffolded.
